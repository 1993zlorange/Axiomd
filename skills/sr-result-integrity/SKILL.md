# 结果完整性检查

沟通方式见 [AGENTS.md](AGENTS.md)：先说结果，用中文解释步骤、依据和限制。

## 什么时候用

分析前需要核对运行数、配置、日志、退出状态、模型保存点和评价脚本是否完整时。按用户的任务自然使用，不要求用户说出技能名，也不要求指定负责人姓名。

## 先看什么

先读用户提供的材料和项目中与这项任务直接相关的文件，明确要回答的问题、已有结果和当前限制。已有手算、草图或研究笔记可以作为比较依据；没有时直接开展工作，不补造人工判断，也不要求用户先完成一套表格。

## 怎么做

1. 按已批准性能矩阵核对实际单元与原始终态，不把检查数量代替实验分母。
2. 核对配置、输入、代码、评价口径及产物身份，区分程序运行、任务完成与科学接受状态。
3. 检查缺失、重复、截断、泄漏或版本差异是否影响性能数据有效性，必要的工程检查仅存内部结构化证据。
4. 保留全部不利结果与失败历史；已有授权内完成必要修复和恢复，排除或改变分析口径时单列真实决定。
5. 仅把影响性能结论的缺陷、有效范围或待重跑项写入相应研究条目，不为检查通过单独产出用户成果文件。

## 交付什么

使用本目录的 [结果模板](assets/output-template.md)。专业内容包括：内部完整性依据：计划/实际单元 / 输入与版本 / 真实终态 / 重复缺失和异常 / 对性能有效性的影响 / 必要恢复；用户研究条目仅引用受影响结果、范围与下一步。

简单问题直接在对话中给出结果；需要保存科研结果时，按项目、上海记录日、规范类型定位唯一日文件。在 `08-项目推进与下一步计划/YYYYMMDD-科研结果-成果卡.md` 追加独立条目，不按任务、Agent、SR、阶段或目录另建文件。每条保留稳定ID、SR身份、来源、状态和适用范围，支持文件加锚点引用；实际专题产物仍在原责任目录。模板表达单条内容，没有真实条目不建日文件，常规实现检查只保留内部证据。

## 怎么检查

计划与实际结果的关系清楚，性能有效性和排除依据可追溯，不静默删除失败或改口径；常规正确性检查不另建科研成果卡或日报条目。

核对关键数字、来源位置、计算或运行结果；明确哪些是事实、解释、假设和计划。缺少输入时完成能做的部分，并说明缺什么、影响什么。没有运行的实验不能写成已完成，没有证据的推断不能写成结论。

## 需要用户决定时

异常剔除、统计解释和主张变化由真实决策者确定；程序已完成与科学接受待确认分开，未涉及的已授权工作继续推进。

已有明确要求或授权就继续；仅当缺失信息会改变研究方向、费用、公开范围或不可逆操作时再提问。普通分析、草稿和本地验证可以直接交付；用户确认是独立状态，不是每项工作的前置签名。需要确认时用推荐、理由和代价说清楚，不从沉默推定同意。

本技能已包含完成任务所需的方法。按需使用本目录资料和现有工具，不加载其他技能，不自动安装扩展，也不自动启动超出授权的下一项研究工作。同一已批准目标内的剩余单元、必要修复、断点恢复、结果汇总和复核属于原任务，不能因叶技能结束、交接、工具等待超时或科学接受待确认而重复索要原授权。超预算、改变科学条件或权限时仅暂停受影响分支。
