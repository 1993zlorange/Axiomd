# Repository layout contract

This contract implements ADR-008 Phase 0/1. It preserves current active evidence paths while preventing new directory drift.

## Stable owners

| Path | Owner and allowed content | Lifecycle rules |
|---|---|---|
| `.codex/` | Project Agent definitions, Skill packages, and Codex project configuration | Maintained source; no browser/test output |
| `src/scienceresearch/` | Product Python code and code-owned static/template assets, following approved architecture boundaries | Maintained source; no databases, screenshots, traces, reports, or ad-hoc probes |
| `tests/` | Automated tests and small immutable fixtures | Maintained test source; generated databases and runs go to `output/` |
| `doc/` | SRS, SDD, architecture, ADRs, user/agent manuals, and maintained governance documents | Maintained documentation; images normally remain in retained evidence paths and are linked relatively |
| `idea/` | Source idea documents and approved prototype/catalog inputs | Source material and a current runtime dependency; no generated evidence or temporary variants |
| `scripts/` | Maintained developer/operator automation that is not a primary root entry point | Maintained source; scripts must resolve approved paths and not create root clutter |
| `data/` | The sole default formal business-data root, including formal artifacts owned by the application | Persistent local state; never use for tests, demos, screenshots, QA, or documentation capture |
| `log/` | `demand_log.md`, `engineer_log.md`, `test_log.md`, and explicitly approved durable logs | Append/update according to role; no raw traces, screenshots, databases, or caches |
| `backups/` | User-requested or application-created formal backups | Recoverable operational data; do not mix with test snapshots |
| `exports/` | User-requested product exports such as PPTX | User-facing output; not a scratch directory |
| `release/<version>/` and release archives | Versioned delivery packages containing source, README, required documents, reports, manifests, and checksums | Immutable after verification; never include formal user data, secrets, caches, or unrelated historical runs |
| `output/project-test/<run-id>/` | Independent QA data and evidence | Isolated per run; existing contract must remain compatible |
| `output/pm-chain-<date>/` | Project-manager journey data and screenshots | Isolated and retained while manuals/reports reference it |
| `output/playwright/` | Current retained browser evidence | Existing active compatibility path; new large runs should use a named/run-id child when practical |
| `output/runs/<run-id>/` | Disposable engineering, smoke, migration, or local verification runs | Isolated and removable after relevant evidence is retained or summarized |
| `output/archive/` | Historical runs and caches retained for audit/recovery | Do not delete blindly; preserve or update manifests when paths are migrated |
| root entry files | `.gitignore`, `agent.md`, `pyproject.toml`, `pytest.ini`, `README.md`, `serve.py`, `run_cli.ps1`, `run_web.ps1` | Stable repository metadata and primary entry points only |

## Placement decision order

For each artifact, decide in this order:

1. Is it maintained product/test/config/documentation source? Place it in its existing owner.
2. Is it formal runtime state, a backup, a user export, or an explicitly requested versioned delivery? Use `data/`, `backups/`, `exports/`, or `release/` respectively.
3. Is it generated by engineering, QA, a browser, a report demonstration, or a migration? Use an isolated `output/` run/evidence path.
4. Is it historical but still needed? Move it into `output/archive/` with provenance, rather than deleting it or leaving it at root.
5. Does no current owner fit? Treat this as an architecture decision; do not invent a directory.

## Prohibited placements

- Root-level databases, screenshots, HTML reports, browser profiles, test runs, smoke directories, caches, extracted packages, and temporary directories.
- Test or demonstration state inside formal `data/`.
- Generated screenshots, traces, databases, exports, or reports inside `src/`, `tests/`, `doc/`, or `idea/`.
- Duplicate directories that differ only by suffixes such as `final`, `final2`, `new`, `copy`, `tmp`, or a milestone name.
- New top-level directories created solely because a tool defaults to the current working directory.
- Long-term junctions or symbolic links used to conceal an incomplete path migration.
- Mutable working data, formal databases, credentials, browser profiles, caches, or unbounded historical evidence inside a release package.

## Run IDs and naming

Use a stable, sortable run ID such as `YYYYMMDD-HHMM-<purpose>` or the existing project convention. A run directory should keep its data, screenshots, traces, reports, and manifest together when practical. Do not call an artifact `final` unless the governing acceptance state is actually final; prefer the purpose and timestamp.

## Migration protocol

For any active path migration:

1. inventory consumers with `rg` across code, tests, documents, HTML, Agent/Skill definitions, scripts, and logs;
2. record source/target paths, file counts, byte counts, and hashes when data or evidence is material;
3. copy to the approved target before changing consumers;
4. update all live references and path policy/configuration;
5. validate links, image signatures, database integrity, tests, browser flows, and packaging as applicable;
6. keep the old path for the agreed compatibility cycle;
7. retire or archive it only after validation and record the rollback method.

ADR-008 currently forbids silently moving `idea/` or `doc/`, and preserves `output/project-test/`, `output/pm-chain-*`, and `output/playwright/` until their consumers are migrated.
