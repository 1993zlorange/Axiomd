# Socratic discovery question map

Choose the smallest question that attacks the largest remaining uncertainty. These are prompts to adapt, not a questionnaire to exhaust.

## 1. Reality of the problem

- When did this problem last occur? What happened from start to finish?
- What workaround is used today, and what does it cost in time, money, errors, risk, or delay?
- Who experiences the pain and who is asking for the solution? Are they the same person?
- What happens if nothing is built for three months?
- Which evidence would convince us that this is only a preference, not a problem?

## 2. Problem versus proposed solution

- If the named feature were forbidden, what outcome would still need to be achieved?
- Which part of the request is the goal, and which part is only the user's current solution hypothesis?
- What existing tool, manual process, or smaller change could achieve the same outcome?
- What measurable gap makes an existing alternative insufficient?

## 3. User and workflow

- Name the first narrow user group and one concrete scenario.
- What triggers the workflow, what input exists, what decision or action follows, and what artifact proves completion?
- How often does it occur, at what scale, and under what pressure?
- Which exception or failure path would make the workflow unsafe or unusable?

## 4. Minimum valuable closed loop

- What is the smallest input-to-result path that creates real value for one user?
- If only one of the requested capabilities can ship first, which one proves the concept?
- Which features are needed for that loop, and which are speculative scaffolding for a future that may not arrive?
- What can remain manual in the first version without invalidating the outcome?

## 5. Scope and priority

- Which three outcomes are Must, and which requested item should be explicitly Won't now?
- If schedule or budget is halved, which outcome must survive?
- Which stakeholder preference conflicts with another, and who has authority to decide?
- What scope addition would cause the project to be re-estimated or split?

## 6. Success, failure, and evidence

- What observable behavior proves this works? Name the test, count, duration, error rate, or retained artifact.
- What result would be disappointing but acceptable, and what result means stop?
- What must never happen?
- Who accepts the result, in which environment, using which evidence?
- Can a tester determine pass/fail without asking what the requirement author meant?

## 7. Constraints and trade-offs

- Which is fixed: time, cost, scope, quality, privacy, offline operation, compatibility, or maintainability?
- When two fixed constraints conflict, which one wins?
- Which data, integration, platform, deployment, or regulatory boundary is mandatory rather than preferred?
- Who maintains the result, and what operational burden is acceptable?

## 8. Assumptions and falsification

- Which single assumption would sink the project if false?
- What is the cheapest test that could disprove it before implementation?
- What contrary evidence have we looked for?
- What would make the user change their mind?
- Are success criteria being moved after evidence arrives?

## 9. Confirmation challenge

Before presenting the contract, ask internally:

- Does the stated solution solve the observed problem or merely reproduce the original request?
- Is every Must required for the minimum loop?
- Did any future feature leak into current scope?
- Are success and failure both measurable?
- Could two competent implementers produce materially different systems while both claiming compliance? If yes, clarify the governing decision.
