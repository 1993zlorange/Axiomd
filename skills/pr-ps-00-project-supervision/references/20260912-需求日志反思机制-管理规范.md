# 需求、日志与反思机制管理规范

## 1. 三类记录不得混用

- 需求记录回答“用户要求什么、为什么、边界和验收是什么”。
- 项目日志回答“实际做了什么、产生了什么、如何验证、还有什么风险”。
- 反思回答“预期与事实为何偏离、根因是什么、最小改进和再验证是什么”。

## 2. 用户要求登记

把用户每次提出的所有要求按原子语义逐项登记，不只保存最终摘要。每项至少包含：需求 ID、提出日期、原意摘要、来源轮次或证据、优先级、范围、非目标、验收标准、状态、影响对象和关闭决定。新增、修改、撤回和冲突都追加记录，不覆盖历史。

明确区分用户明确要求、项目证据事实、Agent 推断和待确认事项。可逆推断可以用于继续工作，但必须记录；会改变范围、架构、成本、权限或验收的推断必须交还用户决定。

## 3. 问题与缺陷登记

用户指出的问题、实际运行错误、测试失败、工具异常、流程遗漏和重复返工均进入问题记录。每项至少包含：问题 ID、发现方式、复现条件、期望、实际、影响、严重度、证据、临时处置、根因状态、负责人和关闭证据。

不得因为问题已修复而省略问题记录；不得把环境阻塞直接写成产品缺陷。

## 4. 日志机制

每个原子动作或运行批次结束后写日志。日志记录任务/需求 ID、目标、实际动作、改动路径、命令、结果、证据、未执行项、阻塞、成本时间和下一步。补记历史日志时必须依据提交、文件、运行或测试证据，且不得覆盖原日志。

日志存放在当前项目 `AGENTS.md` 配置的日志目录。全局 Agent 和全局 Skill 不保存具体项目运行日志。

## 5. 反思触发器

发生以下任一情况时生成反思：用户明确指出问题；出现确认缺陷或回归；同类错误重复；质量门禁阻塞；需求、规则或实现偏离；出现可量化的显著返工；用户要求复盘。一般成功只进入日志，不自动触发规则升级。

反思必须基于目标、实际结果和证据，区分需求、流程、规则、实现、数据与环境根因。一次反思最多提出三项最小改进；涉及权限、目录迁移、核心不变量或新 Skill 时等待人工批准。

## 6. 周期性演化

项目 `AGENTS.md` 应声明评估周期或触发阈值。到期后汇总需求变化、问题类别、反思、质量门结果、耗时和返工，只把跨多次证据支持、边界清晰且不与现有规则重复的规律提议为 Skill/规范优化。先形成技能提案和小范围试点，人工批准后再修改默认规则。
