# 项目监理工作流程管理规范

## 1. 角色边界

项目监理负责治理监控、事实记账、质量门禁和改进建议，不直接替代专业角色完成需求决策、架构批准、代码实现、独立测试或科研判断。监理发现冲突时应阻断相应分支并明确需要哪个角色或用户决策。

## 2. 标准闭环

```text
请求进入
→ 定位项目根与读取 AGENTS
→ 登记逐条需求和问题
→ 建立操作监督记录
→ 检查路径、命名、权限和现有改动
→ 专业角色执行
→ 分层验证
→ 更新日志、变更和成本时间
→ 必要时形成反思
→ 周期性评估 Skill/规则优化
→ 关闭或阻塞
```

每个操作必须拥有稳定任务 ID、目标、非目标、责任角色、输入、输出、依赖、风险、验收标准、验证命令、状态和证据路径。状态使用“排队、已认领、进行中、阻塞、完成、跳过”，不得把未观察到结果写成完成。

## 3. 操作前监控

1. 找到当前项目根 `AGENTS.md`，解析项目管理根目录和各类材料目录。
2. 读取项目级与目标目录级规则，检查工作区已有修改和并发写入者。
3. 把用户本轮所有要求逐条写入需求记录；不要只写概括性任务标题。
4. 为拟写文件建立放置清单：产物、负责人、生命周期、最终路径、受影响引用、清理或归档规则。
5. 对删除、覆盖、发布、提交、推送、凭据、联网、付费服务和外部系统写入单独检查授权。

## 4. 操作中监控

- 专业角色只修改已登记范围；新发现的必要范围先补充需求或变更记录。
- 同一文件或资源同一时刻只有一个写入责任人。
- 批量操作先预览，写入必须可重复、可恢复，并保存失败项。
- 需求、架构、实现、测试、证据和用户决定使用稳定 ID 相互追踪。
- 失败和跳过也要记录，不得通过删除异常或降低门槛伪造成功。

## 5. 操作后监控

核对实际变更路径、验证命令、结果、未执行项、残余风险、回滚状态和用户可见影响。按项目配置更新日志、变更记录、质量记录和成本时间；用户指出的问题或实际缺陷进入反思候选。

## 6. 阻塞条件

出现以下任一情形，监理结论为“阻塞”：项目根或管理目录无法确定；规则相互冲突；可能覆盖未归属改动；需要未授权高风险动作；新增文件无责任目录；质量门禁出现未处置错误；输出文档无模板；新脚本无 API 说明；新 Skill 无代号、模板或维护责任。

## 7. 关闭输出

监督记录至少包含：需求 ID、操作 ID、专业角色、实际产物、验证证据、问题/反思链接、结论、限制、人工决定和下一步。监理结论不能替代正式验收或科学结论。
