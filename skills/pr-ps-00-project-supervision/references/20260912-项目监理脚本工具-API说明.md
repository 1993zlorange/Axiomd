# 项目监理脚本工具 API 说明

## 1. 通用约定

四个工具均为 Python 命令行接口，要求 Python 3.11 或更高版本。`--project-root` 必须显式提供；路径可为相对路径或绝对路径，但工具解析后必须确保所有写入位于项目根内。默认只输出预览，提供 `--write` 才执行项目内写入。日记录没有真实条目时不得创建空白文件。

统一退出码：`0` 成功、预览完成或同一事件幂等未写入；`2` 命令行参数错误；`3` 项目根或TOML配置/路径错误；`4` 记录输入、类型、身份或目标冲突；`5` 读写失败。

## 2. `ps_01_create_governance_document.py`

用途：按项目记录策略预览或安全追加当天同类型记录；`script-api`保留独立对象文档生成方式。

```text
python ps_01_create_governance_document.py \
  --project-root <项目根> --type <规范类型或中文别名> \
  --summary <本条事项标题> [--entry-file <真实条目JSON>] [--write]
```

`--summary`是日文件中的条目标题，不参与当天文件名。同类型存在时继续追加，不能换summary、Agent或运行ID另建文件。无`--entry-file`只预览目标；`--write`缺真实内容时报错，不生成占位。带条目但不带`--write`只校验和预览。

### 类型和项目策略

- 通用过程记录：`requirement`、`supervision`、`log`、`reflection`、`change`、`cost`、`quality`，及`skill-proposal`、`document-type`、`placement`。
- 科研条目：`achievement`、`work-contract`、`handoff`、`decision`；软件项目使用这些类型时必须显式给出合适目录，不强放入科研目录。
- 类型接受已登记中文别名，如“日志”“项目日志”“质量门禁”，先归一后定位。
- 根AGENTS的`project-supervision.record_policy_registry`指向现有功能注册表，其中`record_policy`可声明`project_id`、`profile`（`software`/`research`）、`effective_date`、`timezone: Asia/Shanghai`、`types`和精确`legacy_paths`。每类型配置`aliases`、项目根相对`directory`、`filename_body`、规范`label`。
- 不使用注册表的既有项目可沿根目录配置解析通用类型；科研profile的科研日记录遵项目配置。所有写入仍限制在项目根内，不安装依赖、访问网络或修改其它项目。

### JSON条目与追加身份

日记录JSON必须给出非空`entry_id`、`event_key`、`content`、`impact`、`status`；`entry_id`使用稳定字母数字、点、下划线或连字符，不是文件名。`attempt_id`区分真实尝试，默认首次尝试。`recorded_at`由工具按实际上海时间记录；`occurred_at`可另填带时区的真实发生时间。

通用软件日志必须有`requirement_id`；科研日志必须有`research_point`和`research_source`。科研成果条目还需真实`sr_id`，正文可按原SR单条专业模板组织。可选`background`、`evidence`来源路径列表、`agent`、`workflow`及`revision_of`；空白结构见[项目日记录条目模板](../assets/20261029-项目日记录-条目模板.md)。

- 同一`event_key + attempt_id`且内容完全相同，返回已有记录位置，不重复写；跨日重试也不复制为新文件。新一天的实际进展使用新事件键。
- 同事件身份或entry_id已存在但内容不同，拒绝覆盖。真实更正提供新entry_id、新的修订事件键和`revision_of`，保留旧条目；真实重跑使用真实新尝试身份，不能借重跑掩盖修订。
- 同文件修订可用原entry_id；跨日修订必须给出`项目相对文件#entry-原条目ID`，来源锚点须存在。
- 工具定位项目内当天规范文件，持有写入锁，核对旧内容版本后临时写入并原子替换。锁忙或发现并发变化则拒绝覆盖；调用者重读后重试，不另开文件。
- 文件采用`schema_version: daily-record/1.0`与project_id/record_date/record_type/record_profile/timezone元数据，每条保存`<!-- daily-entry {JSON} -->`及`entry-<entry_id>`稳定锚点。

预览与实际追加：

```text
python ps_01_create_governance_document.py --project-root <项目根> --type log --summary <本条工作标题>
python ps_01_create_governance_document.py --project-root <项目根> --type 日志 --summary <本条工作标题> --entry-file <真实条目.json> --write
```

### `script-api`对象文档

```text
python ps_01_create_governance_document.py --project-root <项目根> --type script-api --summary <工具或接口名> [--write]
```

API说明按工具/接口对象生成中文实体模板，默认预览、已有目标拒绝覆盖；不与其它工具API强行合并，也不使用日记录追加。发布说明、源码、配置、原始运行和签署原件等不同对象同样保留自己的身份。

## 3. `ps_02_create_project_skill.py`

用途：在当前项目的 `.codex/skills/` 中创建带代号的新 Skill，并在项目管理目录生成技能说明。凡声明会输出文档的 Skill，同时创建中文输出模板。

```text
python ps_02_create_project_skill.py \
  --project-root <项目根> --code <代号> --name <英文名称> \
  --display-name <中文名称> --description <中文触发说明> \
  [--document-output] [--write]
```

`--code` 使用小写字母加两位数字，如 `ds-01`；`--name` 使用小写 kebab-case。目标目录已存在时退出，不合并、不覆盖。

## 4. `ps_03_create_script_tool.py`

用途：按 Python 命名规则创建项目脚本骨架，并在同一批次生成配套 API 说明。

```text
python ps_03_create_script_tool.py \
  --project-root <项目根> --module-name <snake_case名称> \
  --summary <中文内容简述> [--write]
```

脚本目录优先读取项目配置中的 `scripts_root`，未声明时读取 `engineering_root` 下既有 `scripts/`；如果目标目录不存在，只有 `--write` 且项目配置允许时才创建。脚本与 API 文档任一目标已存在则整体退出，避免半覆盖。

## 5. `ps_04_validate_management_document.py`

用途：只读校验管理文档是否符合《管理文档写作标准》，或在改写前后比较编号、数字、路径三类令牌是否守恒。

```text
python ps_04_validate_management_document.py <文档.md> [--level A|B|C] [--strict]
python ps_04_validate_management_document.py --baseline <原稿.md> --revised <改写稿.md> [--strict]
```

单文档模式检查级别、结构、公文词、裸编号、路径、代码格式和长句；daily-record/1.0文件按独立条目结构、身份和证据检查，不把整个日文件当一个任务。新生成文档必须带 `writing_level`；对缺少该字段的既有文档，可用 `--level` 显式指定级别进行审计，此时仅提示元数据缺失，不作为错误。比较模式额外检查 frontmatter 是否未变、用户引文和留痕行是否逐字保留，以及令牌多重集是否守恒。警告在 `--strict` 下阻断；校验通过不证明文档事实正确。

## 6. 安全与幂等

- 不访问网络、凭据、Git 提交或外部系统。
- 不接受越出项目根的配置路径。
- 对象生成工具不覆盖已有文件；日记录仅在身份一致且结构有效时安全追加，拒绝静默改写历史。
- 同一真实事件重复追加幂等；不同内容使用新修订身份，冲突不通过改名或换目录绕开。
- 写入失败时报告已创建路径，不把部分写入声明为成功。


## 科研日志追加约定（2026-10-30）

新科研日志须提供report_contract=group-meeting/1.0、work_kind、research_point/research_source、guide_questions、research_question/actions/result/interpretation/limitations/next_step/evidence。performance/analysis还须comparison_conditions/metrics。字段与实际来源校验失败则不写入；不因日志缺项终止授权实验。task_skill可表达非SR科研写作任务，不伪造SR编号。旧记录不回填时间。


## 项目精简记录模式

项目record_policy.process_record_profile=minimal时，新日记录仅允许enabled_daily_types中的requirement和log；不逐任务生成监督、变更、反思、质量、成本、成果卡、工作契约或交接书，也不换名专题报告规避。新增要求、范围和用户决定进入需求，实际研究产物保留唯一专题正文，有意义的科研进展进入日志；原始运行、必要检查、恢复断点和简短接续指针保存在已有工程运行中，不另造人工内部日报。检查与独立评审仍执行，原始意见、真实批准及签署原件保留。没有新要求或实质进展时，两类文件也不必生成。读取真实产物，不把缺少管理表作为阻塞。以下旧类型模板只供未启用该模式的项目或读取历史材料使用。
