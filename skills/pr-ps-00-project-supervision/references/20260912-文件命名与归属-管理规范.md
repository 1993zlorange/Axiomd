# 文件命名与归属管理规范

## 1. 总原则

先确定文件责任、生命周期和目录，再确定名称。项目路径来自项目根 `AGENTS.md`，不得在 Agent、Skill、模板或脚本中写入机器绝对路径。现有目录不得为美观而移动；只有具体项目和具体产物确有责任位置时，才创建缺失目录并同步项目目录说明。

## 2. 命名矩阵

| 文件类别 | 命名规则 | 示例形态 |
|---|---|---|
| Codex Skill | `<代号>-<英文技能名称>`；代号和名称均使用小写字母、数字、连字符 | `pr-ps-05-skill-authoring` |
| Skill 入口 | Codex 固定名 `SKILL.md`；目录名/frontmatter `name` 承担代号与技能名 | `.codex/skills/<代号>-<技能名称>/SKILL.md` |
| 过程记录 | 项目＋上海记录日＋规范类型唯一；固定主体由配置决定，事项为文件内独立条目 | `YYYYMMDD-项目变更-变更记录.md` |
| 正式技术/对象文档 | 对象有唯一当前入口，按真实版本日期维护；不把过程记录换名规避日归并 | `YYYYMMDD-接口设计-技术方案.md` |
| 日志 | 同日只写一个规范文件，任务/Agent/模块/目录/run ID/格式不拆文件 | `YYYYMMDD-科研进度-日志.md`或软件项目固定“项目进度”主体 |
| 反思 | 当日同类型一个文件，问题各为独立条目；仅实际触发才写 | `YYYYMMDD-问题改进-反思.md` |
| 模板 | `YYYYMMDD-内容简述-模板.md` 或相应格式 | `YYYYMMDD-质量门禁-模板.md` |
| Python 模块/脚本 | `snake_case.py`，使用明确职责名 | `validate_manifest.py` |
| Python 类/异常 | `PascalCase`；异常以 `Error` 结尾 | `ProjectConfigError` |
| Python 函数/变量 | `snake_case`；函数使用动作动词 | `resolve_project_root` |
| Python 常量 | `UPPER_SNAKE_CASE` | `SUPPORTED_TYPES` |
| 测试文件 | `test_<行为或对象>.py` | `test_document_creation.py` |
| 配置文件 | 项目既有规范；新配置采用 `snake_case` 或工具约定固定名 | `quality_gate.toml` |
| Schema/契约 | `<领域>_<对象>_v<主版本>.<格式>` | `run_manifest_v1.schema.json` |
| 数据文件 | `<数据集或对象>-<分区或范围>-<版本>.<格式>`；避免空格和机器路径 | `samples-train-v1.parquet` |
| 迁移脚本 | `<序号>_<动作>_<对象>.py` 或项目框架固定格式 | `001_add_run_status.py` |
| Notebook | `YYYYMMDD-内容简述-实验或分析.ipynb` | `YYYYMMDD-误差分布-分析.ipynb` |
| 图表/截图 | `YYYYMMDD-对象-视图或状态-证据.<格式>` | `YYYYMMDD-任务列表-空状态-证据.png` |
| 运行产物 | 置于稳定 `run_id` 目录，文件名表达对象、阶段和版本 | `<run_id>/metrics-v1.json` |
| 模型/检查点 | `<模型>-<阶段或步数>-<版本>.<格式>`，另有 manifest 与哈希 | `model-best-v1.safetensors` |
| API 文档 | `YYYYMMDD-工具或接口简述-API说明.md` | `YYYYMMDD-清单校验工具-API说明.md` |

项目编程规范对具体语言或框架有更严格约束时，以项目规范为准；偏离通用命名必须在项目 `AGENTS.md` 或 ADR 中记录理由。

## 3. 文件放在哪里

优先用户指定位置和当前项目已有目录。代码、测试、数据和发布物保持各自用途；管理记录仅在确有需要时保存。缺少 project-supervision 配置不阻止普通文件操作。

新类型文件沿用最接近的目录与命名规则，说明用途即可，不要求先建立登记表或指定姓名。

## 4. 同日同类型记录规则

1. 唯一键是项目ID、`Asia/Shanghai`实际记录日、规范记录类型。同用途别名先归一，例如日志/项目日志/科研日志，质量检查/质量门禁；文件扩展名、目录、任务、Agent、阶段和scope均不增加拆分维度。
2. 从根 `project-supervision.record_policy_registry` 指向的既有功能注册表读取 `record_policy`。类型到唯一目录、固定主体和规范标签一对一；目录为项目根相对路径，不能写机器路径或按任务临时猜目录。
3. 写前定位当天母版，已有则追加独立条目。稳定entry_id与事件/尝试身份用于去重和引用，不进入日文件名。跨日重试同一已记录事件且内容未变时仍引用原记录，不新建当天副本；新一天真实进展使用新事件键。
4. 每条保留真实时间、需求/研究要点、结果、影响、证据和自己的状态。文件元数据有project_id、record_date、record_type、record_profile、timezone及schema_version；科研叶任务的SR/Agent/工作流属于条目，不能用全文件状态覆盖全部事项。
5. 更正使用新的条目和修订事件键并指向revision_of；原文/原ID和发生时间不改。多写入者由单一写入者/锁协调，读后版本变化则重新读取合并，不覆盖或另开“最终版2”。实际记录日与发生日不一致时如实分别记录。
6. 没有真实条目不创建文件，不每日补齐所有类型，不把每原子动作都塞进当天文件。科研日志只记录研究要点和性能进展；工程检查机器事件留在原run，不人工另造第二份内部日报。
7. 科研成果卡、工作契约、交接书的日文件由项目规则确定唯一落点；每个真实叶任务/交接保留独立条目与锚点，实际研究正文仍在专题目录。正式方案、API说明、论文、图表、源码、配置、固定输入、原始run、模型、发布包和签署原件按对象/版本保留，不强并成日记。
8. 只读导出必须引用真实日记录母版，不独立续写；不同格式不是第二活动记录。旧件保持只读，legacy_paths仅显式登记精确历史文件，不能以目录前缀豁免新稿，也不能靠自标archived让新重复文件逃避检查。历史未实际归并前不称物理唯一，不自动移动或删除旧件。

文件名与条目字段是两个层次：固定主体用于文件，任务标题用于条目。API等真正对象文档沿对象身份维护；任务执行过程属于相应日记录，不能把相同过程换成“专题报告”逃避合并。

## 5. 固定名称例外

工具链强制的 `AGENTS.md`、`README.md`、`SKILL.md`、`pyproject.toml`、`openai.yaml`、`__init__.py` 等固定名称保留。例外只覆盖文件名，不免除目录归属、中文正文、变更记录和验证要求。

项目技术契约也可使用稳定入口名，例如 `PROGRAMMING_STANDARDS.md`、`docs/api.md`、`docs/architecture.md`。稳定入口的版本变更、审计、日志和正式交付记录仍使用日期化文件名；不得用固定名例外规避功能身份、责任人、测试映射或质量门禁。


## 工程文档按对象维护

docs仅保存当前代码的使用与维护说明：README导航、architecture实际结构、api接口导航，以及interfaces、commands、algorithms、adr。相同模块、脚本组或文件格式维护唯一当前正文，使用稳定对象名，日期与适用版本放元数据，不因修复或每次运行新增日期API文档。简单脚本优先--help及必要注释，相关脚本共用运行指南；复杂独立工具确需说明时维护一份对象文档。文档必须讲输入输出、错误、限制及真实命令，不能以目录模板补造未实现能力。

工作契约、工程交付/复验、检查成绩、修订流水、补丁和源码快照不进入docs，必要原始证据留既有run。旧的“每个新脚本新增日期API说明”要求由本节替代；这是维护现行说明，不取消必要用法文档。科研结果、图表解释和主张归achieve并引用唯一原始来源。架构决定按实际决定对象保留，不为普通修复或文件整理另写ADR。

迁移前检查当前代码、配置、命令及历史来源绑定；被封存运行绑定的原件不得覆盖、改指纹或改写旧manifest。保留原路径只读例外须逐文件登记原SHA与用途并在导航标明非现行稿，其余旧件移出日常docs。归并先提取有效字段、边界及运行语义，过程部分原件保全。文档唯一性按对象/适用版本判断，不把不同模块同日的合法文档并成一个日文件。新目录有实际文档才建，工程检查不进入科研日志。
